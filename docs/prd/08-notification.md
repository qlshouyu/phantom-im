# 通知推送 PRD

> 版本：v0.1 ｜ 优先级概览：P0 为主，多端推送抑制为 P1 ｜ 上级文档：[PRD 总纲](README.md)

## 1. 功能概述

通知推送解决的核心问题是：当用户没有打开 Phantom IM（App 处于后台或未启动）时，如何让用户及时获知有新消息到达，同时兼顾隐私保护与打扰控制。推送是离线用户与产品之间唯一的实时触点，直接影响消息必达的用户信任度，因此离线推送到达能力为 P0。

本功能域包含：离线推送触达（依托 APNs/FCM 及国内厂商推送通道）、推送内容展示样式（含隐私模式）、@提醒与免打扰的推送联动规则、多端在线时的推送抑制、用户可控的推送设置项、角标未读数。本文档聚焦产品层的规则定义（"推送应该在什么情况下、以什么内容到达"），不展开推送通道选型、消息队列等具体技术实现。

## 2. 用户场景（User Story）

1. 作为经常不在电脑前的用户，我希望在离线时收到新消息的系统推送通知，以便第一时间知道有人找我，不错过重要沟通。
2. 作为注重隐私的用户，我希望推送通知可以只显示"你收到一条新消息"而不展示具体内容，以便在他人瞥见我的锁屏时不泄露聊天隐私。
3. 作为活跃于多个群聊的用户，我希望即使某个群被我设置为免打扰，只要有人在群里 @我，我依然能收到推送提醒，以便不错过与自己直接相关的信息。
4. 作为习惯在电脑前长时间办公的用户，我希望桌面端保持活跃使用时，手机不要为同一条消息重复推送提醒，以便减少不必要的打扰。
5. 作为用户，我希望能在设置中一键关闭所有推送，或单独关闭推送内容预览，以便按照自己的使用习惯管理通知体验。

## 4. 关键交互流程

### 4.1 离线推送触达

1. 用户 A 处于离线状态（App 未在前台，长连接已断开或进入低功耗保活状态），用户 B 向其发送一条消息。
2. 服务端判定用户 A 当前所有设备均不处于"在线可直接下发"状态，触发推送流程。
3. 服务端根据用户 A 的隐私设置（是否隐私模式）、免打扰设置生成推送内容，通过对应平台的推送通道（APNs/FCM/厂商通道）下发到用户 A 的注册设备。
4. 用户 A 设备系统展示通知栏消息，同时刷新 App 图标角标数字。
5. 用户 A 点击通知，App 启动并跳转至对应会话，客户端建立连接并拉取该会话最新消息，标记为已读。

### 4.2 推送内容生成（含隐私模式判断）

1. 服务端在生成推送文案前，先读取用户的"推送内容预览"开关状态。
2. 若预览开关为"开启"，按消息类型生成摘要：文本消息展示发送者昵称+消息前 20-30 字；图片/语音/视频/文件等非文本消息展示发送者昵称+类型占位符（如"[图片]""[语音]"）；群聊额外展示群名称。
3. 若预览开关为"关闭"（隐私模式），一律生成统一文案"你收到一条新消息"，不包含发送者昵称、群名称或消息内容。
4. 生成的推送文案交由推送通道下发。

### 4.3 免打扰与 @提醒联动判断

1. 服务端收到一条新消息，判定接收方所在会话的免打扰状态。
2. 若会话未设置免打扰，直接按 4.1 流程正常推送。
3. 若会话已设置免打扰，进一步判断该消息是否包含对当前用户的 @提醒（含 @所有人）。
4. 若命中 @提醒，仍触发推送（推送文案可附加"[有人@你]"标识，隐私模式下仍统一展示为"你收到一条新消息"）；若未命中 @提醒，则不触发推送，仅静默更新未读数与角标。

### 4.4 多端在线推送抑制

1. 服务端维护用户各设备的在线与活跃状态（在线是否可达、是否处于前台活跃使用）。
2. 新消息到达时，服务端检查该用户是否存在处于"前台活跃"状态的桌面端或 Web 端设备。
3. 若存在活跃的桌面端/Web 端，服务端不向手机端下发本条消息的推送（消息仍通过长连接实时同步到桌面端），仅静默更新手机端角标与未读数。
4. 若用户桌面端从活跃转为一段时间无操作（进入非活跃/锁屏状态），服务端解除抑制，后续新消息恢复向手机端正常推送。

### 4.5 推送设置变更

1. 用户进入"设置 - 通知"页面。
2. 用户可分别操作：推送总开关、推送内容预览开关。
3. 客户端将变更实时同步至服务端，服务端更新该账号的推送策略配置，即时生效于后续所有推送判定。

### 4.6 通知栏合并与折叠

1. 同一会话在短时间窗口内（如 3-5 分钟）产生多条新消息，且用户此期间始终未打开该会话。
2. 服务端或客户端本地通知管理逻辑检测到同一会话已存在未读通知，不再逐条追加新通知，而是更新为汇总样式，如"张三：[共 5 条新消息]"。
3. 若窗口期内消息来自不同会话，各会话分别独立展示，不跨会话合并。
4. 用户点击汇总通知后，跳转进入对应会话并定位到最新消息，通知栏中该会话的通知随之清除。

### 4.7 首次使用的通知权限引导

1. 用户完成注册或首次进入某个聊天会话，触发通知权限引导时机判断。
2. 若系统检测到用户尚未对本 App 授权通知权限，展示引导浮层，说明"开启通知，消息不错过"。
3. 用户点击"去开启"，跳转至系统通知权限设置页完成授权；点击"暂不"则关闭浮层，本次会话不再重复弹出。
4. 若用户后续在设置页主动开启系统权限，App 内的推送总开关默认同步为开启状态。

## 5. 验收标准

**NT-01 离线推送触达**
- Given 用户 A 处于离线状态，When 用户 B 向用户 A 发送一条文本消息，Then 用户 A 的设备在数秒至数十秒内收到系统推送通知。

**NT-02 推送内容摘要**
- Given 用户已开启推送内容预览，When 收到一条来自好友"小明"的文本消息"晚上一起吃饭吗"，Then 推送通知展示为"小明：晚上一起吃饭吗"（或经截断的摘要）。

**NT-03 隐私模式**
- Given 用户已关闭推送内容预览（隐私模式），When 收到任意新消息，Then 推送通知统一展示为"你收到一条新消息"，不包含发送者昵称或消息内容。

**NT-04 免打扰不推送**
- Given 用户已对群聊"周末爬山群"设置消息免打扰，When 该群产生一条未 @当前用户的普通消息，Then 用户设备不收到该消息的推送通知，仅未读数与角标静默更新。

**NT-05 @提醒穿透免打扰**
- Given 用户已对群聊"项目群"设置消息免打扰，When 群内某成员发送消息并 @了当前用户，Then 用户设备仍收到该消息的推送通知。

**NT-06 推送总开关**
- Given 用户已关闭推送总开关，When 收到任意新消息（含 @提醒），Then 用户设备不收到任何推送通知。

**NT-07 预览开关**
- Given 用户已关闭推送内容预览开关，When 收到新消息，Then 所有推送通知（含 @提醒消息）均按隐私模式文案展示，不出现具体内容。

**NT-08 角标数字**
- Given 用户当前共有 3 个会话存在未读消息，未读总数为 12，When 用户查看 App 图标，Then 角标显示数字 12。

**NT-09 单聊/群聊独立免打扰**
- Given 用户对好友"小红"的单聊设置了免打扰，但未对群聊"家庭群"设置免打扰，When 两者同时产生新消息，Then 小红的单聊消息不推送，家庭群的消息正常推送。

**NT-10 多端推送抑制**
- Given 用户桌面端当前处于前台活跃使用状态，When 好友发来一条新消息，Then 消息实时同步到桌面端，但手机端不触发本条消息的推送通知。

**NT-11 点击跳转**
- Given 用户设备通知栏展示一条来自"小明"的推送通知，When 用户点击该通知，Then App 启动（或从后台唤起）并直接跳转到与小明的聊天会话页面。

**NT-12 通知合并**
- Given 用户 5 分钟内未打开与"项目群"的会话，该群在此期间产生了 5 条新消息，When 用户查看通知栏，Then 仅展示一条汇总通知"项目群：共 5 条新消息"，而非 5 条独立通知。

**NT-13 权限引导**
- Given 用户首次完成注册且尚未授权系统通知权限，When 用户首次进入任意聊天会话，Then 界面展示通知权限开启引导浮层，用户点击"去开启"后跳转至系统权限设置页。

## 6. 边界与异常场景

- **推送通道故障或超时**：推送通道（APNs/FCM/厂商通道）出现下发失败或超时时，服务端应记录失败状态并进行有限次数重试（如间隔重试 3 次），仍失败则不无限重试，避免消息堆积；用户重新上线后仍可通过长连接与消息漫游正常获取该消息，不影响消息本身的可达性。
- **系统通知权限被关闭**：用户在系统设置中关闭了 App 的通知权限，App 内应能感知该状态并在合适位置（如设置页"通知"入口）提示"系统通知权限未开启，可能无法收到新消息提醒"，引导用户前往系统设置开启。
- **短时间大量消息的推送风暴**：同一会话（尤其是活跃群聊）短时间内产生大量消息时，不应逐条推送造成通知栏刷屏，应按 NT-12 合并策略，将同一会话在短时间窗口内（如数分钟）的多条消息合并为一条"共 N 条新消息"的汇总通知。
- **免打扰与 @提醒并发多条消息的合并展示**：某免打扰会话短时间内既有普通消息又有 @提醒消息，仅 @提醒消息触发推送，且推送文案应体现"有人提到你"而非与普通消息合并成无区分度的汇总。
- **在线状态判断误差导致的抑制失误**：由于网络延迟等原因，服务端对桌面端"是否活跃"的判断可能存在短暂滞后，可能导致本应推送的消息被误抑制；产品策略上应以"宁可多推送、不可漏推送"为原则，即状态判断存疑时优先推送，避免用户错过消息。
- **App 被系统强制杀死后的角标同步**：手机 App 进程被系统回收后，角标数字应仍由系统级推送服务维护更新，不依赖 App 前台运行；用户重新打开 App 后角标与实际未读数应保持一致。
- **隐私模式与预览开关的优先级**：隐私模式本质上是"推送内容预览"关闭后的表现形式，二者是同一开关的一体两面，不存在独立冲突；免打扰与 @提醒的联动规则（NT-04/NT-05）优先于内容展示规则（NT-02/NT-03）判断"是否推送"，内容展示规则仅决定"推送展示什么"。
- **消息撤回后的通知栏处理**：撤回操作发生时，若对应推送仍展示在系统通知栏且技术上可操作（部分平台支持撤回/更新已下发通知），应尝试移除或替换该通知；若平台不支持该能力，则允许该通知保留原文案，作为已知限制记录（P2 能力，不影响 MVP 交付）。
- **推送权限从开启变为关闭的过渡处理**：用户此前已授权系统通知权限并正常接收推送，某次在系统设置中主动关闭权限后，App 内推送总开关应同步显示为"系统权限未开启"的不可用提示态，而非仍展示为已开启但实际收不到推送的误导状态。
- **推送 Token 失效**：设备更换、App 卸载重装或系统级推送凭证过期会导致原推送 Token 失效，服务端应在检测到推送持续下发失败（如收到通道返回的无效 Token 错误码）后停止向该 Token 继续下发，并等待客户端下次启动时重新注册新 Token，避免无效重试消耗资源。
- **多设备均离线的推送去重**：用户手机、平板等多台移动设备均已注册推送且均处于离线状态时，同一条新消息应仅向每台已注册设备各触发一次推送，不因消息在服务端的多次状态流转（如先入库后分发）而重复下发。

## 7. 依赖关系

- 依赖 [消息能力](03-messaging.md) 中的消息类型定义，用于生成不同消息类型的推送摘要文案。
- 依赖 [会话列表](06-conversation.md) 中定义的免打扰、未读数规则，推送触发判断以其为准绳。
- 依赖 [多端同步与漫游](07-multi-device.md) 中的多端在线状态判断，用于实现多端推送抑制（NT-10）。
- 依赖 [账号与用户体系](01-account.md) 提供的设备推送 Token 注册与管理能力。
- 与 [群聊](05-group-chat.md) 中的 @提醒机制联动，决定免打扰会话下推送是否穿透。

推送到达能力（NT-01）与多端推送抑制（NT-10）看似存在张力——前者要求"消息不错过"，后者要求"减少打扰"——实际上二者共同服务于同一个原则：**用户应当被有效触达，而不是被无差别触达**。多端在线状态是判断"是否已经有效触达"的关键依据，只有当没有任何在线设备能实时呈现消息时，才需要借助系统推送这一层触达手段，这也是本文档与 [多端同步与漫游](07-multi-device.md) 深度耦合的原因。
