# 多端同步与消息漫游 PRD

> 版本：v0.1 ｜ 优先级概览：P0（全平台核心能力）｜ 上级文档：[PRD 总纲](README.md)

## 1. 功能概述

Phantom IM 定位为全平台通用社交 IM，用户会在手机、桌面（Windows/macOS）、Web 三类设备之间频繁切换。多端同步与消息漫游解决的核心问题是：**无论用户从哪台设备、在什么时间登录，都能看到一致、完整、实时的会话与消息状态**，不出现漏消息、重复消息、状态不一致（如已读/未读、置顶、免打扰在不同端表现不同）等破坏信任感的问题。

本功能域包含四个子能力：
1. **多端在线策略**：定义哪些设备可以同时在线、何种情况下互相顶替。
2. **消息漫游**：消息在云端持久化存储，任意登录设备均可拉取完整历史，而不依赖单一设备本地存储。
3. **状态多端同步**：已读回执、未读数、免打扰、置顶、草稿等会话状态在多端间保持强一致。
4. **设备管理与扫码登录**：让用户掌控自己账号在哪些设备上登录，并提供便捷的扫码登录方式。

多端同步与消息漫游是 Phantom IM 区别于单端产品的核心差异化能力，直接决定"全平台"定位是否成立，因此本文档在 MVP 范围内是 P0 优先级最高、拆解最细的功能域。

## 2. 用户场景（User Story）

以下场景覆盖了多端在线、消息漫游、状态同步、设备安全管理、便捷登录五个维度，是本文档需求拆解的直接来源。

1. 作为一名同时使用手机和电脑办公的用户，我希望手机、桌面端、Web 端可以同时在线并保持消息实时同步，以便我从手机切换到电脑时无需重新收发消息、不会遗漏任何一条。
2. 作为一名刚更换了新手机的用户，我希望登录后能自动拉取此前所有的聊天记录，以便查看完整的历史对话上下文，而不是从一片空白开始。
3. 作为一名习惯在电脑上处理消息的用户，我希望我在电脑上点开的消息，在手机上也同步标记为已读，以便不会重复查看或产生"未读数不一致"的困惑。
4. 作为一名注重账号安全的用户，我希望能看到当前有哪些设备登录了我的账号，并可以远程下线不熟悉的设备，以便及时发现异常登录并保护隐私。
5. 作为一名经常需要在电脑上办公聊天的用户，我希望用手机摄像头扫描电脑/网页端的二维码即可完成登录，以便不必在电脑上手动输入账号密码。

## 4. 关键交互流程

### 4.1 多端同时在线与建立连接

1. 用户在设备 A（如手机）完成登录，客户端与服务端建立长连接，标记设备类型为"手机"。
2. 用户在设备 B（如桌面端）使用同一账号登录，建立独立长连接，标记设备类型为"桌面"。
3. 服务端识别到设备 A（手机）与设备 B（桌面）属于不同设备类型，均保留在线，互不影响。
4. 用户在设备 C（Web 端）登录，若此前已有 Web 端会话在线，服务端向旧 Web 会话推送"被顶替下线"通知，旧会话断开连接并在界面提示"账号已在其他 Web 端登录"。
5. 三类设备（手机、桌面、Web）各自维持独立长连接，服务端为该账号维护"多端在线路由表"，用于后续消息与状态的多端分发。

### 4.2 新设备登录与消息漫游拉取

1. 用户在新设备完成登录鉴权。
2. 客户端向服务端发起会话列表拉取请求，服务端返回该账号名下全部会话（含最后一条消息摘要、未读数、置顶、免打扰状态）。
3. 用户进入某一会话，客户端按"由近及远"分页拉取该会话的历史消息（默认拉取最近一页，如最近 20-50 条），用户上滑加载更早消息时继续分页拉取。
4. 拉取过程中若消息量较大，采用游标分页（基于消息序列号或时间戳），避免一次性拉取造成长时间等待。
5. 拉取完成后，本地展示与云端历史完全一致，用户可无缝查看任意时间点的历史对话。

### 4.3 断线重连与增量补齐

1. 客户端网络中断，长连接断开，客户端进入"离线补齐待触发"状态，本地仍可查看已缓存的历史消息。
2. 网络恢复后，客户端重新建立长连接，携带本地已知的最新消息序列号/同步游标。
3. 服务端比对该游标与服务端最新状态，将断线期间产生的增量消息、状态变更（已读、撤回、免打扰、置顶等）批量下发。
4. 客户端按序列号顺序合并增量数据到本地，刷新会话列表与消息流，保证与服务端最终一致。

### 4.4 已读状态多端同步

1. 用户在设备 A 打开某会话，客户端上报"已读至消息序列号 N"。
2. 服务端记录该账号在该会话的已读位置，并向该账号名下其余在线设备（设备 B、C）广播已读状态变更事件。
3. 设备 B、C 收到事件后，立即将本地对应会话的未读数刷新为 0（或相应减少），并将序列号 N 及之前的消息标记为已读态。
4. 若设备 B、C 当前离线，则在其下次上线建立连接时，通过增量同步流程（4.3）补齐该已读状态。

### 4.5 消息撤回多端一致性

1. 用户在设备 A 对已发送消息发起撤回操作（需满足撤回时限，详见 [消息能力](03-messaging.md)）。
2. 服务端校验撤回权限与时限后，将该消息标记为"已撤回"，并向发送方全部在线设备与接收方（含群聊全部成员）全部在线设备广播撤回事件。
3. 各端收到事件后，将本地对应消息气泡替换为"该消息已撤回"提示，草稿框、引用等引用该消息的场景同步更新为失效提示。
4. 离线设备重新上线后，通过增量同步流程获取撤回事件，本地历史消息同样呈现为已撤回。

### 4.6 扫码登录

1. 用户在桌面端或 Web 端打开登录页，客户端向服务端申请一个带时效性（如 5 分钟）的登录二维码令牌，页面展示对应二维码。
2. 用户使用已登录的手机端"扫一扫"功能扫描该二维码，手机端识别令牌并请求服务端校验。
3. 手机端展示确认页（含请求登录的设备类型、大致地理位置），用户点击"确认登录"。
4. 服务端将该令牌标记为已确认，桌面端/Web 端页面（通过长轮询或长连接监听该令牌状态）感知到确认事件，自动完成登录跳转。
5. 若二维码超过时效未被扫描或确认，页面提示"二维码已过期，点击刷新"。

### 4.7 设备管理与远程下线

1. 用户进入"账号与安全 - 设备管理"页面，客户端拉取当前账号名下全部在线设备列表。
2. 列表展示每台设备的类型图标、设备名称/型号、登录时间、最近活跃时间、大致登录地点，并标注"本机"。
3. 用户对非本机设备点击"远程下线"，客户端发起下线请求。
4. 服务端将该设备的长连接强制断开，并向该设备推送下线通知（若仍在线则立即弹窗提示"账号已在其他设备远程下线"）。
5. 设备管理列表刷新，移除已下线设备。

### 4.8 免打扰/置顶/草稿的会话状态批量同步

1. 用户在新设备登录，或已登录设备重新建立长连接时，客户端在拉取会话列表（见 4.2 步骤 2）的同时，一并获取每个会话当前的免打扰、置顶、草稿状态字段，无需为这三类字段单独发起请求。
2. 用户在任一在线设备上变更某会话的免打扰/置顶状态，客户端先行乐观更新本地界面，同时将变更请求发送至服务端。
3. 服务端持久化该状态变更，并作为一条独立的状态同步事件广播给该账号名下其余全部在线设备。
4. 若某设备在事件广播时处于离线，则在其下次上线时通过 4.3 节的增量同步流程一并获取该状态变更，保证最终一致。
5. 草稿字段遵循相同的广播机制，但为降低同步频率对性能的影响，客户端对草稿内容的上报做输入防抖（如停止输入 2 秒后才上报一次），而非每次按键都实时同步。

### 4.9 设备类型判定与在线路由维护

1. 客户端在建立长连接时，随登录请求上报设备类型（手机 / 桌面 / Web）及设备唯一标识。
2. 服务端在"多端在线路由表"中记录该账号下各设备类型当前对应的连接实例，实现"按设备类型分组"的在线管理。
3. 当同一设备类型出现新的登录连接时，服务端对比路由表中该类型已有的连接实例，触发 MD-02 定义的互踢逻辑。
4. 路由表同时作为消息与状态广播的分发依据：服务端向账号名下"全部在线连接"广播事件时，实际是遍历路由表中记录的各设备类型当前连接实例逐一下发。
5. 设备下线（主动登出、远程下线、连接超时）时，服务端从路由表中移除对应记录，避免向已失效连接重复下发数据。

## 5. 验收标准

**MD-01 多端同时在线**
- Given 用户已在手机端登录且保持在线，When 用户在桌面端使用同一账号完成登录，Then 手机端不受影响仍保持在线状态，两端均可正常收发消息。

**MD-02 同类型端互踢**
- Given 用户已在 Web 端 A 保持登录在线，When 用户在另一浏览器/设备打开 Web 端 B 并登录同一账号，Then Web 端 A 收到下线通知并断开连接，界面提示"账号已在其他 Web 端登录"。

**MD-03 / MD-04 消息漫游**
- Given 用户的账号在云端已有 3 年前至今的全部聊天记录，When 用户在一台全新设备上登录，Then 客户端可成功拉取到该账号名下全部历史会话，且进入任意会话均可查看到完整历史消息，无时间范围限制。

**MD-05 增量补齐**
- Given 设备处于断网状态 10 分钟，期间该账号收到 5 条新消息，When 设备恢复网络并重新建立连接，Then 客户端在数秒内自动补齐这 5 条消息，且消息顺序与服务端一致，无重复、无遗漏。

**MD-06 多端顺序一致性**
- Given 用户在设备 A 与设备 B 同时打开同一会话，When 该会话有新消息到达，Then 设备 A 与设备 B 展示的消息顺序完全一致。

**MD-07 已读状态同步**
- Given 用户在手机端与桌面端同时在线，某会话有 3 条未读消息，When 用户在手机端打开该会话并阅读，Then 桌面端该会话的未读数在数秒内同步刷新为 0。

**MD-08 未读数同步**
- Given 用户桌面端与 Web 端同时在线，When 桌面端某会话未读数因新消息变为 5，Then Web 端该会话未读数同步显示为 5。

**MD-09 免打扰同步**
- Given 用户在手机端对某群聊开启"消息免打扰"，When 用户切换到桌面端查看该群聊，Then 该群聊在桌面端同样显示为免打扰状态，且不再触发桌面通知。

**MD-10 置顶同步**
- Given 用户在 Web 端将某会话置顶，When 用户切换到手机端查看会话列表，Then 该会话同样显示在置顶区域。

**MD-12 发送一致性**
- Given 用户在手机端向好友发送一条消息，When 消息发送成功，Then 手机端与用户其余在线设备（如桌面端）均只展示这一条消息，不出现重复气泡。

**MD-13 撤回一致性**
- Given 用户在桌面端撤回 2 分钟前发送的一条消息，When 撤回操作成功，Then 发送方全部在线设备与接收方全部在线设备中，该消息均被替换为"消息已撤回"提示。

**MD-14 / MD-15 设备管理**
- Given 用户账号当前有手机、桌面、Web 三台设备在线，When 用户进入设备管理页面，Then 可看到三条设备记录，包含设备类型、登录时间、活跃时间与登录地点；When 用户对桌面端设备点击"远程下线"，Then 桌面端设备被强制断开，设备管理列表中该记录消失。

**MD-16 扫码登录**
- Given 用户在 Web 端展示登录二维码，When 用户使用已登录的手机端扫描并确认，Then Web 端在数秒内自动完成登录，无需手动输入账号密码。

**MD-11 草稿同步**
- Given 用户在手机端某会话输入框中输入了未发送的文字"明天下午三点开会"，When 用户切换到桌面端打开同一会话，Then 桌面端输入框中自动展示"明天下午三点开会"，用户可继续编辑或直接发送。

**MD-17 二维码时效性**
- Given Web 端展示的登录二维码已生成超过 5 分钟未被扫描，When 用户此时查看该二维码，Then 页面提示"二维码已过期"，并展示"点击刷新"按钮，用户点击后生成新的二维码。

**MD-18 设备数量上限**
- Given 用户账号已有 5 台设备在线（达到策略上限）且无可顶替的同类型设备，When 用户尝试在第 6 台新设备上登录，Then 登录被拒绝，界面提示"登录设备数已达上限，请先下线其他设备"。

## 6. 边界与异常场景

- **弱网环境下的同步延迟**：在弱网条件下，已读/撤回等状态同步事件可能延迟到达，客户端应展示"同步中"的过渡态而非直接报错，并在恢复网络后自动补齐，不需要用户手动刷新。
- **消息漫游首次拉取超时**：账号历史消息量巨大（如超过 10 万条）时，首次登录不应一次性拉取全部数据，而是先拉取会话列表与每个会话最近一页消息，其余历史采用用户滚动到顶部时的分页懒加载策略，避免登录耗时过长。
- **拉取失败重试**：消息漫游拉取请求失败（网络异常、服务端超时）时，客户端应自动重试（如指数退避重试 3 次），仍失败则展示"加载失败，点击重试"，不应阻塞已缓存内容的展示。
- **撤回与离线设备的时序冲突**：设备离线期间消息被撤回，该设备重新上线后应优先处理撤回事件，确保本地展示直接呈现为"已撤回"，而不是先展示原始消息内容再瞬间替换（避免用户看到不该看到的已撤回内容）。
- **草稿多端并发编辑冲突**：用户在设备 A 和设备 B 同时编辑同一会话的草稿且均未发送，采用"最后编辑时间戳更新覆盖"策略，即最后一次保存的草稿覆盖此前版本；若检测到冲突（两端在极短时间窗口内均有编辑），以服务端接收时间较晚的一份为准。
- **设备数量超限**：单账号在线设备数超过策略上限（如同类型设备最多 1 台在线，总在线设备数上限为 5 台）时，新登录设备优先顶替同类型旧设备；若无同类型设备可顶替且已达总量上限，则拒绝登录并提示"登录设备数已达上限，请先下线其他设备"。
- **扫码登录二维码过期**：二维码超过时效（如 5 分钟）未被扫描，页面自动提示过期并展示"刷新二维码"按钮；若二维码已被扫描但用户在手机端超时未确认，同样判定为过期。
- **远程下线自身设备的保护**：设备管理列表中当前操作设备不提供"远程下线"入口，避免用户误将自己当前使用的设备下线导致会话中断。
- **网络抖动导致的重复推送/乱序**：客户端与服务端均需基于消息唯一 ID 做幂等去重，收到重复的同步事件时直接丢弃，不重复渲染；消息展示顺序以服务端下发的序列号为准，而非客户端本地接收时间。
- **多端消息发送并发冲突**：用户几乎同时在两台设备上向同一会话发送不同消息，服务端按接收先后统一分配序列号，各端均以服务端序列号排序展示，不以本地发送时间为准，避免顺序错乱。
- **状态同步事件的丢失兜底**：若因服务端异常导致某次状态广播事件（如免打扰变更）未能成功下发到某在线设备，该设备不应长期停留在错误状态；客户端应支持定期（如每次前后台切换或每隔固定时间）主动发起一次会话状态全量比对请求，发现与服务端不一致时以服务端为准纠正本地状态。
- **草稿同步与本地误操作的冲突**：用户在设备 A 已清空草稿（等同于删除），几乎同时在设备 B 输入了新草稿内容并保存，两个操作均上报服务端时，以服务端接收时间戳较晚的操作为最终生效结果；"清空"与"新增"同样遵循此时间戳比较规则，不做特殊优先级处理。
- **登录时会话数量巨大导致的首屏卡顿**：账号拥有的会话总数极多（如超过 500 个）时，会话列表首次拉取应仅返回按最近活跃时间排序的前若干页，其余会话随用户下滑分页加载，避免登录后主界面渲染阻塞或长时间白屏。
- **扫码登录被恶意扫描的风险提示**：手机端确认页展示"请求登录的设备类型与大致地理位置"，若该地理位置与用户常用登录地相差较大，产品侧应给予醒目风险提示（如标红展示"非常用地点登录"），提醒用户谨慎确认，避免账号被冒用登录。

## 7. 依赖关系

- 依赖 [消息能力](03-messaging.md) 中定义的消息状态机、撤回规则与消息唯一标识/去重原则，多端一致性建立在其基础之上。
- 依赖 [会话列表](06-conversation.md) 中定义的未读数、置顶、免打扰、草稿字段的产品规则，多端同步的是这些字段的状态变更。
- 与 [通知推送](08-notification.md) 存在联动：多端在线状态是推送抑制（如桌面活跃时手机不推送）判断的输入依据。
- 依赖 [账号与用户体系](01-account.md) 提供的登录鉴权、设备信息采集能力，支撑设备管理与扫码登录。
- 与 [安全与合规](10-security.md) 联动：异常登录/异地登录识别、风控策略影响设备管理页面的风险提示。

多端同步与消息漫游同时是 [PRD 总纲](README.md) 第 7 节"全局非功能性原则"中"消息可靠性""全平台一致性""弱网可用"三项原则最直接的落地功能域：消息漫游确保消息不因设备丢失、卸载重装而永久丢失；MD-07 至 MD-13 定义的各类状态同步需求，是四端信息架构一致性在数据层面的具体体现——用户在任一端看到的会话状态，必须是同一份服务端真值的实时投影，而非各端独立维护的本地状态；本文档第 6 节列出的多数边界场景均以"弱网下先保证本地可用、恢复后自动最终一致"为设计原则，而非要求用户手动干预。
