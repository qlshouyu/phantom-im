# 搜索 PRD

> 版本：v0.1 ｜ 优先级概览：P1 为主，全局搜索基础能力为 P0 ｜ 上级文档：[PRD 总纲](README.md)
>
> ⚠️ **平台化待适配**（见 [01 应用与用户身份 v0.2](01-account.md)）：按手机号搜索陌生用户及其隐私开关失效（平台不存手机号）；保留联系人/群/聊天记录等应用内搜索能力，"搜用户"入参改为 Phantom ID / 昵称。

## 1. 功能概述

搜索解决的核心问题是：随着用户的联系人、群组、聊天记录不断累积，仅依赖会话列表滚动查找已无法满足用户快速定位信息的需求。搜索功能让用户能够通过一个统一入口，跨联系人、群组、聊天记录三类内容快速找到目标，并支持在具体会话内进行精确查找。

本功能域包含：全局搜索入口与结果分类展示、联系人搜索（昵称/备注/ID）、群组搜索（群名/群成员）、聊天记录关键词搜索（按会话聚合、定位到具体消息）、会话内搜索、搜索历史（P2 路线图能力）。

与账号、群聊等其他功能域不同，搜索本身不产生新的业务数据，而是对已有数据（联系人、群组、消息）的一层检索能力，因此本文档的多数需求依赖于其他分档已定义的数据结构，具体依赖关系见第 7 节。搜索能力的价值随用户数据积累而递增——新用户联系人和聊天记录较少时搜索使用频率不高，但随着好友、群组、历史消息不断增长，搜索会逐渐成为用户查找信息的主要路径之一，这也是本功能域虽整体定为 P1、但全局搜索入口与基础检索能力（联系人、群组、聊天记录搜索）仍定为 P0 的原因——它们是搜索价值兑现的最小可用集合。

## 2. 用户场景（User Story）

以下场景覆盖全局检索、按不同字段找人找群、聊天记录回溯、会话内精确定位四类典型使用路径。

1. 作为需要快速找人聊天的用户，我希望有一个全局搜索入口，输入关键词后能同时看到匹配的联系人、群组和聊天记录，以便一步到位找到想要的目标，不必分别进入多个页面查找。
2. 作为记不清对方原始昵称的用户，我希望可以通过备注名或者账号 ID 搜索到联系人，以便即使忘记了对方的昵称也能顺利找到人。
3. 作为加入了多个群组的用户，我希望可以通过群名称或者某个群成员的名字搜索到对应的群聊，以便快速定位到目标群组。
4. 作为需要回忆某次聊天内容的用户，我希望输入关键词就能搜到所有包含该关键词的聊天记录，并按会话归类展示，以便快速判断是哪个会话、进而点击跳转到具体消息位置查看上下文。
5. 作为正在某个会话内查找历史内容的用户，我希望可以直接在该会话内搜索关键词，以便不用退出会话去做全局搜索，也不用手动上滑翻找。

## 4. 关键交互流程

### 4.1 全局搜索

1. 用户点击会话列表页顶部搜索入口，进入搜索态。
2. 用户输入关键词，客户端进行防抖处理后（如停止输入 300ms 后）发起搜索请求。
3. 服务端并行检索联系人、群组、聊天记录三类数据源，返回各自匹配结果（分类返回、限定每类展示条数，如各展示前 5-10 条）。
4. 客户端按"联系人""群组""聊天记录"三个分组展示结果，每组标注匹配总数，超出展示上限时提供"查看全部"入口。
5. 用户可直接点击某条联系人/群组结果进入对应资料页或会话；点击聊天记录结果按 4.2 流程跳转定位。

### 4.2 聊天记录搜索与消息定位

1. 用户在全局搜索结果的"聊天记录"分组中，看到按会话聚合的命中列表（如"与小明的聊天：3 条相关消息""项目群：5 条相关消息"）。
2. 用户点击某个会话分组（或该分组下的某条具体命中消息摘要）。
3. 客户端跳转进入对应会话页面，并自动滚动定位到该命中消息所在位置。
4. 命中的关键词在消息气泡中高亮展示，帮助用户快速确认上下文。
5. 若用户点击的是会话分组（而非具体某条消息），默认定位到该会话内最新一条命中消息。

### 4.3 会话内搜索

1. 用户在某个会话页面内，点击"会话内搜索"入口（如聊天窗口顶部搜索图标）。
2. 用户输入关键词，客户端仅在当前会话的历史消息范围内检索。
3. 搜索结果以列表形式展示命中的消息及其时间，或直接在聊天窗口内以"第 N/共 M 条"形式展示定位进度。
4. 用户可通过"上一条""下一条"按钮在多个命中位置间跳转，聊天窗口自动滚动并高亮当前命中消息。
5. 用户退出搜索态，聊天窗口恢复正常浏览状态。

### 4.4 搜索历史使用（P2）

1. 用户点击搜索入口但尚未输入关键词时，搜索页展示最近的搜索历史词列表。
2. 用户点击某条历史词，直接触发一次相同关键词的搜索，进入结果展示态。
3. 用户可对某条历史词左滑或点击删除图标，单独移除；也可点击"清空历史"一次性清除全部记录。

### 4.5 实时联想与空结果处理

1. 用户在搜索框中逐字输入时，客户端在防抖间隔后（如每停顿 300ms）向服务端发起一次轻量联想请求，仅覆盖联系人、群组两类响应速度快的数据源。
2. 服务端返回按相关度排序的联想结果，客户端在搜索框下方实时展示，用户可直接点击联想项跳转，无需等待完整搜索结果。
3. 若用户输入的关键词在联系人、群组、聊天记录三类数据源中均无匹配结果，客户端展示统一的空状态提示，并给出"换个关键词试试"等引导文案，不展示任何分组标题。
4. 用户清空搜索框内容时，联想结果与空状态提示一并清除，恢复初始搜索态（或展示搜索历史，若已支持）。
5. 若网络延迟导致多次联想请求的响应乱序返回，客户端仅采纳与当前搜索框最新内容匹配的那一次响应，丢弃其余过期响应，避免联想结果与用户当前输入不符。

## 5. 验收标准

**SR-01 / SR-02 全局搜索入口与分类展示**
- Given 用户在会话列表页，When 用户点击顶部搜索入口并输入关键词"小明"，Then 搜索结果按"联系人""群组""聊天记录"三个分组展示，且各分组内容与关键词相关。

**SR-03 / SR-04 / SR-05 联系人搜索**
- Given 用户的好友"张三"备注为"张总"，账号 ID 为"zs8888"，When 用户分别输入"张三""张总""zs8888"进行搜索，Then 三次搜索的联系人分组中均能命中该好友。

**SR-06 群组搜索**
- Given 用户加入了名为"周末爬山群"的群聊，When 用户输入"爬山"进行搜索，Then 群组分组中展示该群聊。

**SR-08 / SR-09 聊天记录搜索与聚合**
- Given 用户与好友"小红"的聊天记录中有 3 条包含关键词"合同"的消息，与群聊"项目群"的聊天记录中有 2 条包含"合同"的消息，When 用户搜索"合同"，Then 聊天记录分组展示两个会话分组，分别标注"3 条相关消息"与"2 条相关消息"。

**SR-10 定位到消息**
- Given 用户在聊天记录搜索结果中点击"与小红的聊天：3 条相关消息"下的某一条具体消息，When 页面跳转完成，Then 用户进入与小红的会话页面，自动滚动并高亮定位到该条命中消息。

**SR-11 会话内搜索**
- Given 用户在与小红的会话页面内，When 用户点击会话内搜索并输入"合同"，Then 检索范围仅限于当前会话，返回该会话内全部 3 条命中消息，不包含其他会话的内容。

**SR-07 群成员搜索**
- Given 用户所在的"项目群"中有一名成员昵称为"李四"，When 用户在全局搜索中输入"李四"，Then 群组分组中展示"项目群"，并标注命中原因为群成员匹配。

**SR-12 会话内上一条/下一条跳转**
- Given 用户在会话内搜索"合同"后共命中 3 条消息，当前定位在第 1 条，When 用户点击"下一条"，Then 聊天窗口自动滚动并高亮定位到第 2 条命中消息，进度提示更新为"2/3"。

**SR-13 空结果提示**
- Given 用户输入的关键词"xyzabc123"在联系人、群组、聊天记录中均无匹配，When 搜索请求完成，Then 页面展示"未找到相关结果"的空状态提示，不展示任何分组标题。

**SR-14 实时联想**
- Given 用户在搜索框中输入"张"，When 输入停顿超过 300ms，Then 搜索框下方实时展示昵称或备注中包含"张"的联系人联想列表，无需用户手动点击搜索按钮。

**SR-15 搜索历史（P2）**
- Given 用户此前搜索过"合同""小明""爬山群"三个关键词，When 用户再次点击搜索入口且尚未输入任何内容，Then 搜索页展示这三条历史记录，用户点击其中任意一条可直接触发对应关键词的搜索。

## 6. 边界与异常场景

- **空关键词或纯空格**：搜索框内容为空或仅包含空格时，不发起搜索请求，搜索结果区域保持空白或展示搜索历史（若已支持），不展示"无结果"提示。
- **搜索结果数量过大**：聊天记录搜索命中结果极多（如超过 1000 条）时，服务端不做全量返回，采用分页返回（如首屏返回最近相关的 20-30 条，用户下滑或点击"加载更多"时继续分页拉取），避免响应过慢或客户端渲染卡顿。
- **已撤回/已删除消息不参与搜索**：消息一旦被撤回或删除，不应再出现在聊天记录搜索结果中；搜索索引需与消息状态变更（撤回、删除）保持同步更新。
- **弱网下搜索请求超时**：网络较差时搜索请求可能超时，客户端应展示加载态，超时后提示"搜索失败，点击重试"，不应无提示地卡在加载状态。
- **特殊字符与表情符号搜索**：关键词包含标点符号、表情符号（emoji）等特殊字符时，搜索应尽量按原始字符精确匹配处理，不因特殊字符导致搜索请求异常或无结果时无提示。
- **群名称重名或高相似度匹配多个群组**：用户输入的关键词命中多个群名相似的群组时，结果按相关度排序展示（如完全匹配 > 前缀匹配 > 包含匹配），并列出全部匹配群组供用户自行辨别选择，不做主观排他性过滤。
- **敏感词与违规内容的搜索限制**：涉及被系统判定为违规、已被治理下架的内容不应通过搜索被检索到，具体治理规则与判定标准遵循 [安全与合规](10-security.md)。
- **搜索历史容量上限（P2）**：搜索历史记录数量达到上限（如 20 条）后，新的搜索词以先进先出方式替换最旧的历史记录，避免无限增长。
- **已退出群聊或已删除好友的历史记录检索**：用户对已退出的群聊、已删除的好友仍有历史聊天记录留存于本地/云端时，这些会话是否出现在聊天记录搜索结果中，遵循与会话列表一致的展示策略——若会话本身已从列表中移除，则搜索结果中也不再展示，避免用户点击后无法进入一个已不存在的会话。
- **超长关键词输入**：用户输入的关键词长度超出合理范围（如超过 50 个字符）时，客户端应做长度限制或提示，避免因构造异常长的查询导致搜索请求失败或服务端处理异常。
- **搜索结果排序的置顶与最近会话优先**：全局搜索的聊天记录分组在命中数量相近时，优先展示消息时间较新的会话在前，同时不因某会话被置顶而额外提升其在搜索结果中的排序优先级——置顶只影响会话列表展示，不影响搜索相关度排序。
- **多语言与拼音搜索的处理边界**：MVP 阶段搜索仅支持按输入的原始文字精确/包含匹配，暂不支持拼音首字母检索或跨语言联想匹配（如中文备注对应英文昵称联想），此类能力留待后续迭代评估，避免在 MVP 阶段引入过重的分词与语义匹配复杂度。
- **黑名单联系人与已拉黑用户的搜索可见性**：用户搜索到已被自己拉黑的联系人时，仍应展示该联系人（用户可能需要查看历史信息或解除拉黑），但不应展示新增聊天入口异常状态之外的其他交互引导，具体交互限制遵循 [关系链](02-relationship.md) 中黑名单机制的定义。
- **搜索请求的频率限制**：为避免用户高频连续输入触发过多请求造成服务端压力，客户端对搜索/联想请求需做合理的防抖与并发控制（新请求发出时取消尚未返回的上一次请求），避免出现结果乱序覆盖（旧请求的响应晚于新请求返回，错误覆盖当前展示内容）的问题。
- **同一关键词命中过多重复片段**：单条消息内关键词重复出现多次时（如"合同合同合同"这类连续重复文本），聊天记录搜索结果中该消息仍作为一条命中记录展示，不因关键词多次出现而被重复计入命中条数或拆分为多条结果。

## 7. 依赖关系

- 依赖 [消息能力](03-messaging.md) 中定义的消息类型与内容结构，聊天记录搜索基于此建立可检索的消息索引。
- 依赖 [关系链](02-relationship.md) 中定义的好友备注、昵称等字段，作为联系人搜索的匹配依据。
- 依赖 [群聊](05-group-chat.md) 中的群名称、群成员数据，作为群组搜索的匹配依据。
- 依赖 [会话列表](06-conversation.md)，聊天记录搜索结果最终指向具体会话并完成跳转定位。
- 与 [多端同步与漫游](07-multi-device.md) 间接相关：消息漫游保证了聊天记录的完整性，是聊天记录搜索"搜得全"的前提——若某条历史消息因漫游能力缺失而未同步到当前设备，则搜索也无法命中该消息。

搜索能力的多端一致性同样值得关注：用户在手机端搜索到的联系人、群组、聊天记录结果，与在桌面端搜索同一关键词得到的结果应保持一致，这是因为搜索本身检索的是服务端统一存储的数据（联系人关系、群组信息、云端消息），而非某台设备的本地数据，因此天然继承了 [多端同步与漫游](07-multi-device.md) 所建立的"服务端数据为唯一真值"的原则，无需为搜索单独设计多端一致性方案。
- 与 [安全与合规](10-security.md) 联动：已被内容治理下架/屏蔽的消息不出现在搜索结果中。
