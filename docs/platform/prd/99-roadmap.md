# 演进路线图

> 版本：v0.1 ｜ 优先级概览：P2+（方向性规划）｜ 上级文档：[PRD 总纲](README.md)

## 路线图说明

本篇描述 Phantom IM 在 MVP 之后的功能演进方向，按"体验增强 → 社交扩展 → 信任与开放"三个阶段展开，对应产品从"能用"到"好用"到"留得住"再到"值得信赖"的成长逻辑。

**本路线图仅代表方向性规划与阶段归属，不代表确定排期。** 每个 Phase 2 及以后的功能在正式立项时，都需要输出独立的 PRD，明确详细需求、验收标准与排期，本篇不替代该过程。

## Phase 1：MVP（已覆盖，简述）

MVP 阶段聚焦"把基础聊天体验做深做透"，已在分档 01-10 中详细展开，包括账号体系、关系链、消息能力、单聊、群聊、会话列表、多端同步与漫游、通知推送、搜索、安全与合规。详见 [PRD 总纲](README.md) 第 4 节"MVP 边界"。

## Phase 2：体验增强

Phase 2 的目标是在 MVP 稳定运行的基础上，补齐用户高频诉求的体验短板，提升用户粘性与跨端效率，不引入新的社交范式。

### 1v1 音视频通话

- **功能简述**：支持好友之间发起一对一语音/视频通话，与文字消息共用会话入口。
- **目标价值**：满足即时沟通场景（比打字更高效），是社交 IM 的常见期望能力，提升用户日均使用时长与留存。
- **与 MVP 功能域的关系**：依托 [单聊](04-direct-chat.md) 的会话与在线状态能力发起通话；通话记录作为一种消息类型，遵循 [消息能力](03-messaging.md) 的消息状态与时序原则；来电提醒复用 [通知推送](08-notification.md)。
- **纳入该阶段理由**：音视频链路（信令、编解码、弱网优化）技术复杂度高，且并非文字聊天体验的前提条件，MVP 阶段优先保障文字消息体验的可靠性，待基础体验稳定后再引入。

### 消息云备份

- **功能简述**：用户可将本地聊天记录加密备份至云端，用于设备丢失或重装后的数据恢复。
- **目标价值**：降低用户更换设备的数据丢失风险，提升长期信任感，是多端重度用户的核心诉求。
- **与 MVP 功能域的关系**：与 [多端同步与漫游](07-multi-device.md) 的消息漫游能力互补——漫游解决"近期消息任意设备可见"，云备份解决"长期/完整历史的持久化保存"。
- **纳入该阶段理由**：消息漫游已在 MVP 覆盖核心的多端一致性需求，云备份属于锦上添花的容灾能力，可在体验增强阶段补齐。

### 聊天记录迁移

- **功能简述**：支持用户更换手机时，将聊天记录从旧设备迁移到新设备（含本机直连迁移与云端迁移两种方式）。
- **目标价值**：降低换机流失率，是用户换机时的高频痛点。
- **与 MVP 功能域的关系**：依赖消息云备份能力作为迁移的数据来源，也与 [多端同步与漫游](07-multi-device.md) 的设备管理机制相关。
- **纳入该阶段理由**：迁移功能依赖云备份先行落地，故排在云备份之后，同属体验增强阶段。

### 桌面端效率增强（多窗口等）

- **功能简述**：桌面端支持多会话独立窗口、消息多开、快捷键操作等效率型功能。
- **目标价值**：满足多设备工作者在电脑端长时间高强度使用的效率诉求，强化桌面端差异化体验。
- **与 MVP 功能域的关系**：在 [会话列表](06-conversation.md) 与 [单聊](04-direct-chat.md)/[群聊](05-group-chat.md) 的基础上做桌面端专属的交互增强，不改变核心消息模型。
- **纳入该阶段理由**：MVP 阶段桌面端与移动端保持信息架构一致即可满足基本可用性，效率增强属于桌面端场景的深化打磨，可在体验增强阶段推进。

## Phase 3：社交扩展

Phase 3 的目标是从"一对一/群组沟通工具"向"社交平台"扩展，引入非即时性的内容分享与更丰富的社交表达方式。

### 动态 / 朋友圈

- **功能简述**：用户可发布图文/视频动态，好友可查看、点赞、评论。
- **目标价值**：拓展社交场景到非实时的内容分享维度，提升用户打开频次与社交黏性，是 MVP 明确排除但长期看是社交 IM 的重要增长点。
- **与 MVP 功能域的关系**：动态的可见范围复用 [关系链](02-relationship.md) 的好友与分组体系；动态互动的通知复用 [通知推送](08-notification.md)。
- **纳入该阶段理由**：动态是独立于即时消息的新产品模块，涉及内容生产、Feed 分发、隐私可见范围等复杂设计，且依赖 [安全与合规](10-security.md) 的内容治理能力先行成熟，故安排在社交扩展阶段而非 MVP。

### 表情商店

- **功能简述**：提供官方/第三方表情包的浏览、下载、收藏与在聊天中使用。
- **目标价值**：丰富消息表达的趣味性与个性化，是社交产品常见的轻量变现与用户活跃抓手。
- **与 MVP 功能域的关系**：作为 [消息能力](03-messaging.md) 中表情类富消息的内容来源扩展，MVP 阶段仅提供系统内置表情。
- **纳入该阶段理由**：表情商店涉及内容供给（版权、审核上架）与运营体系，非聊天基础能力，可在社交扩展阶段与动态等内容型功能一并规划。

### 群直播 / 群通话

- **功能简述**：支持群内发起多人音视频通话或群直播，用于群体协作、社群活动等场景。
- **目标价值**：满足社群场景下的多人实时互动需求，是群聊从"文字协同"升级为"多媒体协同"的关键能力。
- **与 MVP 功能域的关系**：依赖 Phase 2 的 1v1 音视频通话能力向多人场景扩展，同时基于 [群聊](05-group-chat.md) 的成员与权限体系控制发起与加入权限。
- **纳入该阶段理由**：多人音视频的技术复杂度（媒体服务器选型、并发承载）显著高于 1v1 通话，需在 1v1 能力稳定后再扩展至群场景，故排在社交扩展阶段。

## Phase 4：信任与开放

Phase 4 的目标是在产品成熟、用户规模稳定后，向更高的隐私信任标准与生态开放能力演进。

### 端到端加密（E2EE）

- **功能简述**：消息内容仅在收发双方设备上可解密，服务端无法读取明文，可选择性开启（如"私密聊天"模式）。
- **目标价值**：满足对隐私安全要求更高的用户群体，提升产品的信任背书，是即时通讯产品的长期竞争壁垒之一。
- **与 MVP 功能域的关系**：与 [多端同步与漫游](07-multi-device.md) 的服务端消息漫游存在天然冲突——漫游依赖服务端保存可查询的消息副本，E2EE 要求服务端不可读明文；也影响 [安全与合规](10-security.md) 中依赖服务端扫描明文的内容风控机制。
- **纳入该阶段理由**：E2EE 涉及密钥管理、多端密钥同步、离线消息处理等复杂机制，且与现有漫游架构存在根本性权衡，需要独立的技术方案评估，故安排在信任与开放阶段，晚于社交扩展。

### 开放平台 / 机器人 API

- **功能简述**：向第三方开发者开放消息收发、群管理等能力的 API，支持机器人账号接入群聊/单聊。
- **目标价值**：构建生态，让工具类、通知类第三方服务接入 Phantom IM，扩大产品的使用场景边界。
- **与 MVP 功能域的关系**：基于 [消息能力](03-messaging.md) 与 [群聊](05-group-chat.md) 的能力做 API 化封装，机器人账号需要 [账号与用户体系](01-account.md) 支持特殊账号类型。
- **纳入该阶段理由**：开放平台需要成熟的内部能力与稳定的账号体系作为前提，且涉及额外的安全审核（Bot 权限、调用频控、API 鉴权），适合在产品成熟后规划。

### 小程序

- **功能简述**：在 Phantom IM 内嵌入轻量第三方应用（小程序），可通过聊天入口分享与打开。
- **目标价值**：进一步延展平台边界，承接更多轻服务场景（如工具、游戏、电商），提升用户停留时长。
- **与 MVP 功能域的关系**：小程序的分享与打开依托 [消息能力](03-messaging.md) 的卡片消息类型，入口可能出现在 [会话列表](06-conversation.md) 或独立发现页。
- **纳入该阶段理由**：小程序生态依赖开放平台的能力基础（鉴权、API），且需要独立的审核与分发机制，故排在开放平台之后，作为信任与开放阶段的延伸。

## 关于 E2EE 与消息漫游的兼容性说明

E2EE 一旦上线，将与现有 [多端同步与漫游](07-multi-device.md) 分档中"消息云端存储、任意设备登录即可拉取历史"的实现方式产生冲突。届时需要重新评估以下方向并形成独立技术方案：

- 是否采用"设备端密钥加密后仍存储服务端密文，由收信设备本地解密"的漫游兼容方案
- 是否将 E2EE 限定为可选的"私密聊天"模式，与默认的漫游模式并存
- 新增设备登录时的历史消息可见范围如何处理（如仅同步开启会话后的消息）

该评估应作为 E2EE 正式立项 PRD 的前置工作，不在本路线图展开。
