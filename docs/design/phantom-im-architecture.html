1概述

1.1背景与目标

Phantom IM 定位为 IM 开发平台（PaaS）：接入方在自己的 App 中集成 Phantom IM SDK，在自己的服务端通过 OpenAPI 管理用户与应用配置。平台不提供 C 端账号体系，用户身份仅为 Phantom ID；注册、登录凭证、隐私与注销由接入方用户体系承担，鉴权改为接入方服务端签发 UserToken（PRD 01 v0.2）。

架构需要达成的核心目标：

  • 消息可靠：不丢、不重、不乱序是底线，服务端与客户端双侧保证。
  • 多端一致：手机 / 桌面 / Web 三类设备同时在线，已读、会话状态、草稿跨端同步 MD-01 MD-05。
  • 永久漫游：历史消息永久保存，新设备可分页回溯 MD-03。
  • 低成本起步、按需演进：初期单体部署，规模上来后按瓶颈逐个拆分，业务代码零改动。

1.2范围

本期纳入

完整协议栈（长连接 + HTTP API + 同步机制 + 媒体通道）；单聊、群聊（≤500 人）、会话列表、多端同步与漫游、通知推送、搜索、安全合规；OpenAPI 管理面；应用级阅后即焚。

MVP 不纳入

音视频通话、动态 / 朋友圈、端到端加密、云备份、平台侧扫码登录（由接入方账号体系实现）。协议已为 CALL_RECORD、CHANNEL、E2EE 预留扩展位（§6.6）。

1.3术语

术语含义
Phantom ID平台内用户唯一标识，全局唯一、跨应用不冲突；由接入方经 OpenAPI 导入时由 external_user_id 映射生成 AC-02
AppID / AppSecret应用标识与密钥。AppSecret 用于接入方本地签发 UserToken，以及 OpenAPI 请求签名
UserToken接入方服务端用 AppSecret 签发的 JWT（HS256），SDK 用它完成 WS 握手与端上 HTTP 调用
Envelope长连接每个 WebSocket 二进制帧承载的 Protobuf 外层结构
会话 Timeline / conv_seq按会话存放完整消息体的有序时间线，conv_seq 为会话内严格递增序号，永久保存
用户同步 Timeline / user_seq按用户存放轻量同步事件的时间线，user_seq 为用户维度严格递增序号，滚动保留 30 天
SyncEvent需要多端感知的变更事件（新消息、撤回、已读、会话状态等 10 类）
扇出（Fanout）/ 写扩散把一条消息为每个接收者各写一份同步事件；本平台纯写扩散
在线路由表记录用户各端连接落在哪个网关实例的 Redis 数据结构（§9.6）
launcher只做依赖聚合与配置的启动工程，决定部署形态（单体 / 拆分）

2.2设计原则

同步链路只做「收单」，其余全部异步化发消息的同步闭环只有：幂等检查 → 分配 conv_seq → 落会话 Timeline → 发事务消息 → 回 SendMsgResp。写扩散、推送、索引、风控全部由 RocketMQ 消费组异步完成。
能用 HTTP 的不占长连接长连接只承载实时、需服务端主动推送的流量；媒体文件本体永不走长连接，先 HTTP 上传拿 mediaId，再发只含元数据的消息。
MQ 止于服务端内部RocketMQ 不直达客户端，最后一公里仍由 WS 网关按协议下发 Envelope，协议层零改动。
单一权威写入方user_seq 只由扇出服务分配，所有进入用户同步 Timeline 的事件都经 MQ 汇入，杜绝并发写序号竞态。
缓存尽力而为，必达靠协议在线路由表允许短暂脏数据；消息必达由「在线推送 + ACK 重推 + Sync 补拉」三级机制保证，不依赖路由表绝对准确。
YAGNI群上限 500，纯写扩散足够，不预留读扩散降级；Typing / Presence 不进 MQ；不用 MQ 广播做多端同步。

5总体技术架构

5.1分层架构

技术上分为六层加一条贯穿的支撑运维层。依赖方向自上而下；业务服务之间不直接依赖，只经契约层或 MQ 事件交互。

5.2各层职责

层组成职责
L1 客户端接入接入方 App（SDK）、接入方服务端SDK 维护本地双 Timeline 缓存、ACK 游标、发送队列与同步引擎；接入方服务端签发 UserToken、调用 OpenAPI
L2 网关接入WS 网关集群、HTTP 接入、OpenAPI 接入Envelope 编解码、多租户验签、心跳、路由表登记与互踢、指令分发 SPI；网关无状态
L3 业务服务13 个业务 module消息收单、扇出、同步 / 漫游、会话、群组、关系、用户、推送、媒体、搜索、风控、OpenAPI
L4 契约与共享内核phantom-api-*、common、proto、infra starter拆合切换枢纽：本地实现存在则同 JVM 直调，否则 gRPC stub 经 Nacos 发现对端
L5 异步消息RocketMQ 5 个 Topic + DLQ事务 / 顺序 / 延时消息，削峰、解耦、可靠性外包
L6 数据存储会话 Timeline、用户同步 Timeline、Redis Cluster、对象存储、搜索索引消息永久存储、同步事件滚动窗口、在线路由与幂等、媒体、检索
支撑与运维Nacos、可观测与告警、第三方推送通道、launchers注册发现、配置下发、监控告警（含 DLQ 堆积）、部署装配

5.3通道职责划分

长连接 WSS + Protobuf

消息发送与接收（Send / Push / Ack）；同步事件拉取（Sync）与已读上报（MarkRead）；信令：输入状态、在线状态订阅、撤回、App 前后台；服务端主动通知：被踢下线、强制登出。

HTTPS + JSON

资料、关系链、黑名单、群管理；会话列表快照与会话状态写入；历史漫游分页、搜索；设备管理、推送 Token、举报、数据导出；媒体分片上传（下载走 CDN 直链）；OpenAPI 管理面。

会话状态写入（置顶等）走 HTTP：它是低频的请求-响应操作。写入成功后服务端产生 ConvStateEvent 进入其他端的同步 Timeline，再经 WS 回到各端，形成「乐观更新 + 广播」闭环。

6通讯协议设计

6.1帧格式

WebSocket binary 帧，每帧一个 Protobuf Envelope：

message Envelope {
  uint32  version = 1;   // 协议版本，当前为 1
  Command cmd     = 2;   // 指令，见 6.2
  uint64  cid     = 3;   // 客户端请求流水号；响应帧回带；服务端主动推送为 0
  int32   code    = 4;   // 响应码，0 成功；请求帧与推送帧为 0
  bytes   payload = 5;   // cmd 对应的报文体（Protobuf 序列化）
}
  • 请求-响应配对：客户端每次请求 cid 单调递增，服务端响应帧回带同一 cid。
  • 三类帧：Req（客户端 → 服务端，期待响应）、Resp（回应 Req）、Push（服务端 → 客户端，cid=0，不需响应；MsgPush 例外，需回 MsgAck）。

6.2指令集

分段域指令
0x0001~0x00FF连接管理AUTH_REQ/RESP PING/PONG KICK_PUSH LOGOUT_REQ/RESP
0x0100~0x01FF消息SEND_MSG_REQ/RESP MSG_PUSH MSG_ACK RECALL_MSG_REQ/RESP RECALL_PUSH
0x0200~0x02FF同步SYNC_REQ/RESP MARK_READ_REQ/RESP READ_RECEIPT_PUSH CONV_DIGEST_REQ/RESP
0x0300~0x03FF信令TYPING_SIGNAL TYPING_PUSH PRESENCE_SUB_REQ/RESP PRESENCE_UNSUB_REQ PRESENCE_PUSH APP_STATE_REQ/RESP

6.3认证握手与在线策略

连接建立后首帧必须是 AuthReq，10 秒内未认证服务端主动断开。

AuthReq {
  access_token          // UserToken：接入方服务端用 AppSecret 签发的 JWT（§10.2）
  device_id             // 客户端生成并持久化的设备唯一标识
  device_type           // MOBILE / DESKTOP / WEB（MD-01 三类设备）
  platform              // ios / android / windows / macos / web
  client_version
  app_id                // 应用标识（AC-01），验签与租户路由依据
  user_id               // Phantom ID，须与 UserToken claims 一致
}
AuthResp {
  server_time           // 服务端时间，供客户端校准时钟偏移
  max_user_seq          // 服务端当前最新 userSeq，客户端据此判断需要同步多少
  heartbeat_interval_s  // 服务端建议的心跳间隔
  burn_after_read       // 应用级阅后即焚配置 { enabled, ttl_seconds }
  read_receipt          // 应用级已读反馈配置 { enabled }
}

认证成功后服务端将 (userId, deviceType, deviceId, connId) 登记进多端在线路由表（§9.6），并执行在线策略：

  • 同类型互踢 MD-02：同 device_type 已有连接时，向旧连接推 KickPush{ reason=SAME_TYPE_LOGIN } 后断开。
  • 设备总数上限 MD-18：超上限且无同类型可顶替时，返回 2005 DEVICE_LIMIT_EXCEEDED，拒绝连接。
KickPush.reason触发
SAME_TYPE_LOGIN同端登录顶替
REMOTE_LOGOUT远程下线 MD-15 / OpenAPI 强制下线 AC-10
TOKEN_REVOKED接入方吊销凭证或禁用用户 AC-06、AppSecret 应急轮换
BANNED平台封禁 SEC-08
SDK 行为约束收到 KickPush 的 SDK 不得自动重连，须回调宿主 App 并透传 reason，由宿主决定后续（引导重新获取 UserToken 或退出）。

6.4心跳与在线判定

  • 客户端按 heartbeat_interval_s 发送 Ping（移动端基线 270 秒，可自适应下调），服务端回 Pong。
  • 服务端连续 2 个周期未收到任何上行帧，判定连接失效，摘除路由表记录。
  • 路由表在线状态是离线推送触发的判定输入 NT-01：某账号无任何在线可达连接时，新消息转入推送流程。

6.5断线重连

  1. 指数退避重连：1s, 2s, 4s, … 上限 60s，每次叠加 ±30% 随机抖动，避免服务端恢复时的重连风暴。
  2. 重连成功 → 重新 AuthReq → 比较 max_user_seq 与本地游标 → 落后则立即 SyncReq 增量补齐 MD-05。
  3. 弱网期间本地缓存正常可读；发送队列中未确认消息按 §8.1 规则重试。

6.6协议演进与兼容

  • Envelope.version 当前为 1；不兼容变更递增版本，网关按版本路由或返回 1004 UPGRADE_REQUIRED。
  • Protobuf 演进：只增不删字段号，废弃字段 reserved，枚举首值为 *_UNSPECIFIED=0。
  • 路线图预留：ConvType 预留 CHANNEL；MsgType 预留 CALL_RECORD（Phase 2 音视频）；E2EE（Phase 4）时 MsgContent 可整体替换为密文封装字段，Envelope / Sync 层无需改动。

7数据架构

7.1标识体系

标识生成方作用
client_msg_id客户端（UUID v4）幂等去重键 MSG-16。服务端按 (sender_id, client_msg_id) 去重，重复提交返回首次结果
msg_id服务端消息全局唯一 ID，撤回 / 引用 / 举报的目标标识
conv_id规则生成单聊：si_ + 双方 uid 升序拼接 hash，任何入口进入同一好友会话必得同一 ID；群聊：gr_ + groupId
conv_seq服务端，会话内严格递增会话内排序唯一依据 MSG-15，漫游分页游标
user_seq服务端，用户全局严格递增同步 Timeline 事件编号，多端增量补齐游标 MD-05
server_time服务端展示时间与撤回窗口判定基准，客户端本地时钟不参与排序

8核心业务流程

8.1消息发送

  • 重发：沿用原 client_msg_id 重新提交，服务端幂等保证不重复落库；排序沿用首次成功的 conv_seq MSG-10。自动重试上限 3 次，之后仅手动。
  • 受限投递 DC-16/18：对方已删除 / 拉黑我时，SendMsgResp 正常返回成功（不透露原因），服务端静默不投递；随后经发送方自己的同步 Timeline 下发 RestrictedDeliveryEvent，客户端插入系统提示气泡。
  • 我方主动受限 DC-15/17：客户端本地拦截；本地状态过期而到达服务端时，返回 3002 NOT_FRIEND / 3003 IN_MY_BLACKLIST。
消息状态机 MSG-09SENDING → SENT → DELIVERED → READ，失败态 FAILED，状态只进不退。DELIVERED 在服务端投递到对方任一在线设备（或对方 Sync 拉到）时经发送方同步 Timeline 下发；READ 见 §8.6。

8.2接收与 ACK 必达

设备级 ACK 游标即「该设备已确认到的 user_seq」，与 SyncReq.since_user_seq 是同一游标：在线推送与离线补拉共用一套进度，不存在两套账。

8.3撤回

  1. RecallMsgReq{ msg_id } → 服务端校验归属（本人；群主 / 管理员按群规则扩展）+ 时间窗口 now − server_time ≤ 120s（以服务端时钟为准）。
  2. 通过 → 会话 Timeline 标记 recalled，写撤回事件进所有相关用户的同步 Timeline，并向在线设备推 RecallPush。
  3. 超时 / 重复撤回 → 4003 RECALL_TIMEOUT / 4004 ALREADY_RECALLED；多端并发撤回时后到者静默同步。
  4. 离线设备经 Sync 拉到的消息已合并撤回态，不会闪现原文。

8.4增量同步

SyncReq{ since_user_seq, limit=200 }
SyncResp{ events[], max_user_seq, has_more, full_resync=false }
  1. 触发：握手后发现落后、任何 Push 中发现 user_seq 跳号、前后台切换。
  2. 客户端循环拉取直到 has_more=false，按 user_seq 顺序原子应用到本地库，每批持久化游标。
  3. 服务端下发前做事件合并：同一消息的「新消息 + 撤回」合并为撤回态；同一会话多次置顶只保留终态。天然满足「撤回优先」。
  4. 重复事件按 user_seq 幂等丢弃。

8.5游标过期与全量重建

流程见图 8-5 右侧分支。since_user_seq 超出 30 天窗口时返回 full_resync=true，客户端放弃事件回放，改走 HTTP 全量重建：

  1. GET /conversations?cursor=… 分页拉会话列表快照（含最后一条消息摘要、未读数、置顶、免打扰、草稿）；首屏只拉最近活跃的前 N 页。
  2. 以快照回包中的 max_user_seq 重置本地游标。
  3. 各会话历史不预拉，进入会话时懒加载（§8.7）。

新设备首次登录 = 本地游标为空 = 同一条全量重建路径，无特殊分支。

8.6已读同步

MarkReadReq{ conv_id, read_conv_seq }   // "已读至 conv_seq=N"，位置式而非逐条式
  • 服务端持久化 (user_id, conv_id) → read_conv_seq，只允许前进。
  • 本人其他端（不受开关影响）：收 ReadPositionEvent，未读数清零 / 减少 MD-07/08。
  • 对端已读反馈（受应用级开关 AC-08 控制，经 AuthResp.read_receipt 下发）：
    • 关闭：不生成 ReadReceiptEvent，客户端不展示任何已读状态；
    • 开启 · 单聊：对端收 ReadReceiptEvent{ reader_id, read_conv_seq }，消息置「已读」；
    • 开启 · 群聊：任一成员已读位置前进时向群成员下发事件，客户端维护「成员 → 已读位置」集合；已读成员 = read_conv_seq ≥ 消息 conv_seq。
  • 放大抑制：按 (conv_id, reader_id) 做 5 秒窗口合并，500 人群单窗口回执量 ≤ 活跃阅读者数。
  • 冷启动补偿：GET /conversations/{conv_id}/read-positions 返回全体成员当前位置快照。
  • 未读数 = max(conv_seq) − read_conv_seq（排除本人消息），服务端为权威值。

8.7历史漫游

GET /v1/conversations/{conv_id}/messages?cursor={conv_seq}&direction=older&limit=50
→ { messages[], next_cursor, has_more }
  • 游标分页由近及远，永久可拉 MD-03/04；direction=newer 支持搜索定位 / 引用跳转后向下补页。
  • 返回的消息已合并撤回态与删除过滤（本人已删除的消息不返回，删除记录按用户维度存储）。
  • 失败指数退避重试 3 次，不阻塞已缓存内容展示。

8.8状态防漂移兜底

广播事件可能因服务端异常丢失。客户端在前后台切换或每 30 分钟发起一次轻量摘要比对：

ConvDigestReq{ digest }         // 本地全部会话状态（置顶/免打扰/未读/read_conv_seq）的哈希
ConvDigestResp{ match, diff[] }  // 不一致时返回差异项，以服务端为准覆盖本地

8.9信令

输入状态 DC-06

TypingSignal 不落库、不进 Timeline、不 ACK，仅向单聊对端在线设备转发。发送侧 3 秒节流，接收侧 5 秒无新信令自动消失。

在线状态 DC-05

订阅制：进入聊天页 PresenceSubReq（≤50 人），离开时退订。状态 ONLINE / AWAY / OFFLINE，离线不透出精确时间。

App 活跃状态

前后台切换上报 AppStateReq{ foreground }，写入路由表 foreground 字段，作为推送抑制的决策输入。

8.10推送决策

推送 Token 经 POST /v1/push/token 注册 / 刷新；通道返回无效 Token 后服务端停发，等待重新注册。

9消息核心架构（RocketMQ）

9.1总体结构

平台化边界：网关完成多租户验签（AppSecret 经配置中心缓存于网关）；OpenAPI 服务承接 server-to-server 管理面，产生的资料 / 关系 / 配置变更统一以 SyncEvent 汇入 TOPIC_SYNC_EVENT，不另设管理事件 Topic。关系链托管为应用级可选能力，业务服务按应用配置启停关系校验。

削峰填谷

500 人群的 1→500 写放大由 MQ 缓冲，发送 RT 与扇出规模解耦。

可靠性外包

消费失败自动重试最多 16 次 + 死信兜底，「不丢」不依赖手写重试。

解耦扩展

新增下游 = 新增一个 Consumer Group，发送主链路零改动。

9.2发送链路

  • conv_seq 分配不进 MQ：由消息服务在同步链路内按会话粒度取号，保证 SendMsgResp 返回时排序已确定 MSG-15。
  • 受限投递：消息服务判定受限后仍返回成功并落会话 Timeline，事务消息携带 restricted 标记，扇出服务只为发送者本人端写事件，并追加 RestrictedDeliveryEvent。

9.3可靠性三要素映射

PRD 硬约束服务端机制客户端协议机制
不丢事务消息（落库与投递原子）+ 消费重试 16 次 + DLQ 告警补偿MsgAck 游标 + SyncReq 兜底
不重消费侧幂等键 msg_id + receiver_id（写 user_seq 事件前查重）client_msg_id 发送幂等 + msg_id 展示去重
不乱序conv_seq 同步分配 + 顺序消息（ShardingKey=conv_id 恒定路由同一队列串行消费）按 conv_seq 排序渲染，按 user_seq 排序回放

9.4Topic 与消费组规划

Topic消息类型生产者消费组说明
TOPIC_MSG_EVENT顺序 + 事务，ShardingKey=conv_id消息服务扇出 / 在线推送 / 离线推送 / 搜索索引 / 风控审计tag 区分 new_msg / recall
TOPIC_SYNC_EVENT普通消息各业务服务扇出服务10 类 SyncEvent 统一入口，由扇出统一分配 user_seq
TOPIC_PUSH_RETRY定时消息（5s）在线推送服务在线推送服务承接「5 秒未 ACK 重推一次」，网关无状态化
TOPIC_MEDIA_PURGE定时消息消息服务媒体清理阅后即焚：全部接收方已读后 ttl+24h 删除媒体；兜底发送后 30 天

  • 顺序消息只用于 TOPIC_MSG_EVENT：状态类事件以服务端合并语义（撤回优先、取终态）容忍乱序，走普通消息换吞吐。
  • 撤回复用消息通道：tag=recall 进入同一顺序队列，保证同会话「先消息后撤回」。
  • 管理面不单设 Topic：OpenAPI 踢下线是即时同步动作（查路由表 → 网关 RPC，不经 MQ）；其余变更走 TOPIC_SYNC_EVENT。

9.5延时重推与网关无状态化

不在网关内存挂定时器（网关重启即丢失），改为：

  1. 在线推送服务下发 MsgPush 的同时，向 TOPIC_PUSH_RETRY 发一条 5 秒延时消息（携带 receiver_id + user_seq）；
  2. 到期消费时对比该用户 ACK 游标：acked_user_seq ≥ user_seq 则丢弃，否则重推一次；
  3. 重推后不再续发，继续未达由客户端 SyncReq 兜底（三级必达的第三级）。

由此 WS 网关完全无状态，可随意扩缩容与滚动发布。

9.6在线路由表

路由表回答一个问题：给某个用户推送时，该投到哪些网关实例的哪些连接上。它是在线推送、离线推送判定、信令路由的共同数据源。

  • 两级：Redis 只回答「该用户在哪些网关上有哪些端」，不持有连接；网关进程内存持有真正的 WebSocket 句柄。
  • 以 device_type 为 field：三类设备各至多一条在线，同类型互踢退化为同 field 覆盖写；多端广播即一次 HGETALL（≤3 条）。
  • 不用 key 级 TTL：TTL 是整 key 粒度，会把三端一起过期；判活规则 now − last_active > 2 × heartbeat_interval。
  • 先比对 conn_id 再删：防止旧连接迟到的断连事件误删刚登记的新连接。
  • 定位为尽力而为的缓存：多推给已死连接无害（无 ACK 走重推 / Sync），漏推有 Sync 兜底，因此清理逻辑无需分布式事务。
  • 多租户：Phantom ID 全局唯一，key 无需 app_id 前缀；app_id 存于记录值内。

10接口设计

10.1通用约定

  • Base：https://api.phantom.im/v1，Content-Type: application/json; charset=utf-8。
  • 统一响应包：{ "code": 0, "message": "ok", "data": {...} }，错误码与长连接共用（§10.6）。
  • 幂等：写操作支持 X-Idempotency-Key 头，服务端 24h 去重。
  • 分页：游标式 cursor + limit，回包带 next_cursor / has_more。

10.2平台化鉴权

身份三层：开发者 → 应用（AppID / AppSecret）→ 用户（Phantom ID）。鉴权分两条链路：

SDK 用户鉴权 · UserToken

接入方服务端用 AppSecret 本地签发 JWT（HS256），claims { app_id, user_id, iat, exp }，exp 建议 ≤7 天、上限 30 天。平台只验签、不回调 AC-03。用于 WS 握手与端上 HTTP。

OpenAPI 服务端鉴权 AC-12

/openapi/* 请求头携 X-App-Id + X-Timestamp + X-Signature（HMAC-SHA256(AppSecret, method+path+body+timestamp)），时间戳偏差 >5 分钟拒绝，按应用限频。

  • 过期与刷新：存量长连接不因过期中断，重连时校验；被拒 2001 TOKEN_EXPIRED 时 SDK 回调宿主取新 Token 自动重连 AC-04。平台不提供 refresh 接口。
  • 秘钥轮换 AC-09：宽限期（≤7 天）内新旧 AppSecret 双秘钥验签；应急轮换宽限期置 0，旧 Token 即刻失效。
  • 强制下线：接入方经 OpenAPI 禁用用户或强制下线 → 在线连接收 KickPush，后续验签返回 2002 TOKEN_REVOKED。

│   ├── phantom-conversation/  phantom-group/  phantom-relation/  phantom-user/
│   └── phantom-push/  phantom-media/  phantom-search/  phantom-risk/  phantom-openapi/
└── phantom-launchers/             # boot-monolith / boot-gateway / boot-core / …
依赖方向强约束（maven-enforcer 校验）launchers → services → service-api / infra / common / proto。services 之间禁止直接依赖，只能依赖 service-api；MQ 事件是服务间另一条合法通路。各 module 各管各的表，禁止跨 module 直读（靠评审约定 + 独立库账号）。

11.2module 内部结构

im.phantom.message
├── adapter/        # 入口适配：网关指令处理器（SendMsgReq）、HTTP Controller
├── application/    # 用例编排：收单流程（幂等→取号→落库→事务消息）
├── domain/         # 领域模型与规则：Msg、conv_seq 取号、撤回窗口判定
├── infra/          # 出口适配：Timeline DAO、MQ 生产、service-api 调用
└── MessageAutoConfiguration.java   # @AutoConfiguration，launcher 引入即生效
  • 每个 module 通过 Spring Boot 自动装配暴露自己，launcher 不做 @ComponentScan 全局扫描，避免单体形态下的隐式耦合。
  • 对外两类表面：service-api 接口的本地实现（@ConditionalOnMissingBean 注册）+ MQ 事件。
  • 网关指令分发采用 SPI：业务 module 注册自己关心的 Command 处理器，网关不依赖任何业务 module。

11.3可分可合切换机制

拆合的唯一变化点在 launcher 的依赖清单与配置，业务代码零改动。

// phantom-api-route 内（示意）
@AutoConfiguration
public class RouteApiAutoConfiguration {
  @Bean
  @ConditionalOnMissingBean(RouteTableService.class)   // 本地实现不存在 → 远程 stub
  RouteTableService routeTableGrpcClient(GrpcChannelFactory f) { ... }
}
  • 合（同 JVM）：launcher 同时引入调用方与被调方，本地实现被自动装配，调用即普通方法调用。
  • 分（跨进程）：launcher 只引入调用方 + phantom-api-*，gRPC stub 兜底，经 Nacos 发现对端。
  • api module 三件套：接口 + DTO（复用 proto 类型）+ gRPC stub 实现。
  • MQ 通路不参与切换：异步链路始终走 RocketMQ，单体也不例外。

11.4构建与版本治理

  • BOM：phantom-dependencies 锁定 Spring Boot 4.x、RocketMQ client 5.x、gRPC、Nacos 等版本；根 pom 只 import BOM。
  • proto 单一来源：从仓库根 proto/phantom/v1/*.proto 生成 Java，与 SDK 共用同一份。
  • 统一版本号：revision 占位符 + flatten-maven-plugin，module 间永远同版本。
  • 质量门禁：enforcer 校验依赖方向、按 module 并行单测、mvn -pl 增量构建配合 CI 变更检测。

13质量属性设计

13.1可靠性：三级必达

① 在线推送

查路由表直推 MsgPush，客户端回 MsgAck 推进设备游标。

② 延时重推

5 秒延时消息检查 ACK 游标，未确认则重推一次。

③ Sync 补拉

事件永远留在同步 Timeline，客户端 SyncReq 按游标补齐。

服务端「不丢 / 不重 / 不乱序」的具体机制见 §9.3。

13.2性能与容量

  • 发送 RT 与扇出规模解耦：同步链路只到会话 Timeline 落库，500 人群写放大由 MQ 缓冲。
  • 路由表：单用户至多 3 个 field，百万同时在线约几百 MB；读写均为 O(1) 单 key 操作，按 user_id 分片水平扩展。
  • 已读回执放大抑制：5 秒窗口合并，回执量与活跃阅读者数相关而非消息数 × 成员数。
  • 同步事件合并：撤回合并、状态取终态，减少下发量。
  • 在线状态订阅制：单次订阅 ≤50 人，避免全量好友状态推送风暴。

13.3可用性与故障恢复

场景表现恢复路径
落库成功、commit 前消息服务宕机half 消息悬挂Broker 回查 → 查到会话 Timeline 有该 msg_id → commit
落库失败half 消息悬挂回查查不到 → rollback；客户端超时重发（client_msg_id 幂等）
扇出服务消费失败自动重试（间隔递增）幂等键防止已写接收者重复；16 次耗尽进 DLQ 告警
扇出滞后（堆积）接收端延迟收到客户端经 SyncReq 拉到已扇出部分；消费堆积告警扩容
推送服务宕机MsgPush 未下发未 ACK 消息重投给同组其他实例；最终 Sync 兜底
网关实例宕机路由表残留脏数据实例心跳 key 失联后清理任务扫除；惰性清理转离线推送
服务端故障恢复大量客户端同时重连指数退避 + ±30% 抖动，避免重连风暴

13.4可扩展性

  • WS 网关无状态（重推交给延时消息），可随意扩缩容与滚动发布。
  • 新增下游能力 = 新增一个 Consumer Group，主链路零改动。
  • 部署形态按瓶颈演进，业务代码零改动（§12）。

13.5安全

  • 传输：全链路 TLS 1.3（WSS / HTTPS），禁明文；移动端证书固定列入客户端实现建议。
  • 认证：UserToken + OpenAPI 签名双链路（§10.2）；WS 连接生命周期内 Token 过期不断连，重连时校验。
  • 内容风控 SEC-10~12：文本 / 图片在 SendMsgReq 处理链内同步扫描，拦截返回 4005；疑似违规先投递 + 异步复审，违规触发系统撤回（operator 标记为系统）。
  • 频控 SEC-13：网关层按 (user_id, cmd) 令牌桶，HTTP 按 (user_id, 路由)；超限 1003 并带 retry_after。
  • 非好友消息请求 SEC-14：会话标记 is_request=true，客户端归入「消息请求」分区、不计主未读；接收方同意后转正常会话。
  • 隐私最小披露：搜索不可见、冷静期、拒收等统一返回 3001 / 3004 类模糊错误。
