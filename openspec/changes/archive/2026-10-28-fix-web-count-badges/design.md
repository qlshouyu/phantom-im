## Context

参见 `proposal.md`。当前 Web IM 的导航未读总数只在 `ChatsView` 挂载时由会话列表求和，离开聊天页后实时监听随组件卸载而停止；当前会话打开时，已读 effect 只依赖会话 ID，后续新消息不会再次触发已读。服务端会话分页已返回排除免打扰会话的权威 `badge_count`，无需新增后端契约。

## Goals / Non-Goals

**Goals:**

- 让导航未读数独立于当前主导航页面持续更新。
- 使用服务端权威汇总值，正确排除免打扰会话。
- 打开会话后按该会话真实未读数扣减，并处理已读与列表刷新竞态。
- 用单一数字角标实现统一 `1-99` 与 `99+` 显示及无障碍语义。

**Non-Goals:**

- 不修改服务端未读投影、OpenAPI 或 protobuf。
- 不修改免打扰会话的非数字未读展示规则。
- 不将文字状态标签或正文中的普通数字缩略为 `99+`。

## Decisions

### 1. App 层维护导航未读状态

在 Web App 层新增会话未读控制器，登录后订阅 `message`、`sync` 和 `conversation` 事件，并通过会话分页的 `badge_count` 获取权威总数。事件刷新采用短防抖合并突发消息，避免每条消息触发多次请求。

替代方案是永久挂载并隐藏 `ChatsView`。该方案改动较小，但仍把全局状态耦合到聊天页，并保留重复刷新与旧快照覆盖风险，因此不采用。

### 2. Gateway 暴露分页汇总字段

Gateway 保留现有 `listConversations()` 供聊天和通讯录使用，同时增加返回分页模型的方法，将 `badge_count` 映射为领域数据。导航角标必须使用该汇总值，而不是只对当前加载页求和，避免分页和免打扰口径错误。

### 3. 已读扣减采用乐观更新加权威校准

用户打开会话后，`ChatsView` 在 `markRead` 成功时上报该会话真实未读数。App 层先扣除对应数量以即时反馈，再刷新 `badge_count` 校准。当前会话的 `maxConvSeq` 增长时重新执行已读，确保聊天框已打开期间到达的新消息不会重新累计未读。

会话刷新使用请求序号或版本标记，仅接受最新响应，防止已读前的旧列表快照覆盖已读结果。

### 4. 使用统一 CountBadge 和格式化函数

新增通用数字角标组件，封装 `count <= 99 ? count : '99+'` 的显示规则，并为真实数量提供无障碍描述。现有不同颜色和大小的角标通过变体或类名复用组件，不复制阈值逻辑。

不使用 CSS 自动裁切来判断“放不下”，因为结果依赖字体和宽度且不可测试。统一采用产品定义的 99 阈值。

## Risks / Trade-offs

- [消息事件集中到达导致频繁刷新] -> 使用短防抖合并 `message`、`sync` 和 `conversation` 事件。
- [旧会话快照晚于已读响应返回，导致角标回弹] -> 使用请求版本，丢弃过期响应，并在已读后执行权威校准。
- [显示为 `99+` 导致读屏丢失真实数量] -> 角标保留真实数量的可访问名称。
- [把所有数字都误改成 99+] -> 仅替换明确的数字角标组件，不处理文字标签和正文数字。

## Migration Plan

纯前端行为修复，无数据库或协议迁移。先引入通用角标和未读控制器，再替换调用点并补充测试；回滚时回退前端构建产物即可，不影响服务端数据。
